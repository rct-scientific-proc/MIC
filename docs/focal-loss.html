Focal loss: why it exists, and how this pipeline leans on it

The loss function in losses.py is the only one this project trains with. This document derives it from ordinary cross-entropy, shows quantitatively why it survives extreme class imbalance, and walks through the four places the codebase exploits its structure.

Section 1

The imbalance problem, concretely

Take a realistic split for this project: 5 genuine classes × 30 samples, plus 25 hard negatives per genuine sample — 150 genuine vs 3,750 hard negatives. Under plain cross-entropy every sample contributes

CE(p_y) = −log(p_y) p_y = softmax probability of the true class

The trouble is not the size of any single loss term — it's the sum. A few epochs in, most hard negatives are already easy: the model assigns them py ≈ 0.9 and each contributes a tiny −log(0.9) ≈ 0.105. But 3,750 samples × 0.105 ≈ 394 total loss, while 150 genuine samples still fighting at py ≈ 0.4 contribute 150 × 0.916 ≈ 137. The gradient is ~3:1 dominated by examples the model has already solved, in exactly the direction that suppresses the minority classes. Scale the imbalance to 100:1 or 1000:1 and the minority signal drowns completely — training converges to "predict hard_negative always", which is a low-loss, useless model.

Classical fixes each address half the problem:

  • Class weighting (α-balanced CE) rescales whole classes — but it cannot distinguish an easy majority sample from a hard one; it dampens both equally.
  • Undersampling throws majority data away — but the samples you drop might be exactly the difficult ones worth keeping.

Focal loss attacks the actual culprit: it down-weights samples by how easy they currently are, per-sample and continuously re-evaluated on every forward pass.

Section 2

From cross-entropy to focal loss

Focal loss (Lin et al., Focal Loss for Dense Object Detection, ICCV 2017 — born from the same problem at 1000:1 scale in one-stage object detectors) multiplies cross-entropy by a modulating factor and a per-class weight:

FL(p_y) = −α[y] · (1 − p_y)γ · log(p_y)

Two independent knobs:

  • (1 − p_y)^γ — the focusing term. When the model is already confident and correct (py → 1) the factor collapses to 0, silencing the sample. When the model is wrong (py → 0) the factor is ≈ 1 and the sample keeps its full cross-entropy voice. γ controls how sharp that transition is; γ = 0 recovers plain CE exactly.
  • α[y] — the class weight, an ordinary prior that scales entire classes independently of difficulty.

Revisiting the Section-1 arithmetic with γ = 2: the easy hard negatives at py = 0.9 are modulated by (0.1)² = 0.01, so their total contribution falls from 394 to ≈ 3.9. The struggling genuine samples at py = 0.4 are modulated by (0.6)² = 0.36, contributing ≈ 49. The gradient balance flips from 3:1 majority-dominated to ~13:1 minority-dominated — without discarding a single sample or touching a class prior. And the weighting is adaptive: if a hard negative starts fooling the model again next epoch, its py drops and its voice returns automatically.

Section 3

What γ actually does — the down-weighting table

The focusing factor for a sample at confidence py (loss reduction relative to cross-entropy):

p_y (true class)γ = 1γ = 2γ = 5reading
0.10.90×0.81×0.59×badly wrong — keeps nearly full loss at any γ
0.50.50×0.25×0.03×borderline — γ=2 quarters it, γ=5 nearly silences it
0.90.10×0.01×10⁻⁵×easy — γ=2 gives a 100× reduction
0.990.01×10⁻⁴×10⁻¹⁰×trivial — effectively removed from training

So γ sets how easy a sample must be before it stops mattering. γ = 2 is the standard default and what --focal-gamma ships with: easy samples fade by two orders of magnitude while genuinely contested samples (p ≈ 0.5) keep a quarter of their voice. Higher γ focuses harder but has a failure mode: at initialization everything is misclassified, so early training rides on a small set of extreme samples and can destabilize — one reason the pipeline pairs the loss with sampling caps rather than cranking γ.

Section 4

What α actually does — and why only one class gets a special value

γ handles the easy/hard axis; α handles the asymmetric cost axis. This project's objective is explicitly asymmetric: missing a genuine snippet (recall failure) is expensive; letting a hard negative through is the thing we fix second, only after recall is secured. losses.py therefore builds the α vector as:

alpha = [1, 1, …, 1, hn_alpha] # genuine classes 1.0, hard_negative from --hn-alpha

With the default --hn-alpha 0.25, an error on a hard negative costs a quarter of an equally-confident error on a genuine sample. The model is told, in the loss itself: prefer false accepts over false rejects. That bias shows up exactly where the pipeline wants it — the genuineness score distribution shifts so that high recall is reachable at a higher threshold, which is what the post-hoc threshold sweep then exploits.

α and γ compose rather than compete: γ decides which samples within every class deserve gradient; α decides how much each class's mistakes cost. The original paper found the two interact (its best pairing was γ=2, α=0.25 for the rare class — note their α weighted the rare class low because the focusing term already favored it; here the α semantics serve the recall-first objective instead, weighting the majority hard-negative class down).

Section 5

How this code takes advantage of the loss

5.1 The implementation itself

log_p   = F.log_softmax(logits, dim=1)          # numerically stable: never log(softmax(x))
log_p_y = log_p.gather(1, targets.unsqueeze(1)).squeeze(1)
p_y     = log_p_y.exp()
loss    = -self.alpha[targets] * (1 - p_y).pow(self.gamma) * log_p_y

Three deliberate choices: log_softmax (a fused, stable kernel — computing log(softmax(x)) separately overflows for large logits); the α vector registered as a buffer so it moves to the GPU with the module and survives checkpointing; and no reduction — the forward returns one loss per sample, and the training loop takes .mean() itself. That last choice is not cosmetic; it is what enables 5.2.

5.2 Per-sample losses feed the hard-negative miner

Focal loss produces, for free, a continuously-updated difficulty signal: a hard negative's per-sample loss is high precisely when the model currently confuses it with a genuine class. The training loop hands the unreduced loss vector to the miner every batch:

per_sample = criterion(logits, labs)     # (B,) — no reduction
loss = per_sample.mean(); …backward…
miner.update(idxs, per_sample)           # EMA: score ← 0.7·score + 0.3·loss

When --imbalance-ratio forces subsampling, the sampler draws the next epoch's hard negatives in proportion to these scores. The loss and the sampler form a loop: focal loss measures which hard negatives are dangerous → the miner schedules them → the loss focuses on them when they arrive. The same quantity drives both attention mechanisms, at two timescales — γ within a batch, mining across epochs.

5.3 α is a live training knob, not a constant

Because α is just a buffer, set_hn_alpha() can change it between epochs at zero cost. The pressure ramp uses this: with --hn-alpha 0.1 --hn-alpha-end 1.0 --ramp-epochs N, the hard-negative class's cost rises step by step, and each step is gated on the recall target being met — the loss gets stricter about specificity only as fast as recall can bear. The α schedule and the imbalance-ratio schedule move together, so cost and exposure rise in lockstep.

5.4 Division of labor with the threshold sweep

Nothing in the loss guarantees the recall target — and that's intentional. The loss's job is to shape the score distribution: push genuine samples' genuineness scores up and hard negatives' down, so the two populations separate. The post-hoc validation sweep then guarantees the target by choosing the operating threshold. Focal loss makes the achievable specificity-at-target-recall higher; the sweep banks it. Loss = optimization pressure, threshold = contractual guarantee.

One measurable side effect: heavily down-weighting easy samples means the model gets little gradient pressure to push confidences toward 0 or 1, so scores tend to be less overconfident than plain CE — but not calibrated either. That is why evaluate.py ships a calibration curve and ECE: the threshold is always swept, never assumed to sit at a probability-meaningful value like 0.5.
Section 6

Practical guidance

  • Start with the defaults (γ=2, hn-α=0.25). They are the well-tested regime; the imbalance ratio and ramp give you enough control without touching the loss shape.
  • Minority recall stuck low? Lower --hn-alpha (0.1) and/or tighten --imbalance-ratio toward 1.0 before raising γ — exposure and cost fixes are gentler than curvature fixes.
  • Specificity plateaued below what you need? Ramp α up (--hn-alpha-end 1.0, or beyond 1 in stubborn cases) with --ramp-epochs, rather than jumping it — the gate protects recall while the pressure rises.
  • Loss ≈ 0 but validation flat? With focal loss a near-zero training loss is normal once most samples are easy; judge progress by the validation columns in metrics.csv (recall, specificity, AUROC), never by the raw loss magnitude.
  • Raising γ above 2 is a last resort for extreme imbalance that mining + ratio caps can't tame; expect noisier early epochs and consider a lower learning rate to compensate.
Summary Cross-entropy spends gradient in proportion to how many samples say something; focal loss spends it in proportion to how much each sample still has to teach. In this pipeline that principle is used three times over: inside the batch (γ), across classes (α, ramped), and across epochs (per-sample losses driving the hard-negative miner) — with the threshold sweep converting the resulting score separation into a guaranteed operating point.
